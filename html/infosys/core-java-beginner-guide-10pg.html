1. == vs equals()  ·  2. hashCode() & equals() Contract

1. == vs equals()

== = same memory address (reference). equals() = same content/value (when overridden). For objects, always use equals() to compare values.
a ──► ["Hello"] (0x100) b ──► ["Hello"] (0x200) ← different object c ──► same as a a==c → TRUE a==b → FALSE a.equals(b) → TRUE (same text)

Primitives: == compares values directly. Integer trap: Integer a=100,b=100 → a==b true (cached -128..127). 200==200 false (new objects).

String a=new String("Hi"), b=new String("Hi");
a==b;       // false — different objects
a.equals(b);// true  — same content
int x=10,y=10; x==y; // true — primitives
Type==equals()
ObjectsSame reference?Same value?
PrimitivesCompare valuesN/A
Q: == vs equals()?
== compares addresses. equals() compares content. Always equals() for objects unless checking same reference.

2. hashCode() & equals() Contract

Rule 1: if a.equals(b) → a.hashCode()==b.hashCode() MUST hold
Rule 2: Same hashCode ≠ equals() true (collision OK)
Rule 3: Override BOTH together — always!
Analogy: hashCode() = shelf number in library. equals() = check exact book. Equal books MUST be on same shelf — else HashMap can't find them.
HashMap lookup: 1. hashCode() → bucket index 2. equals() → exact key in bucket Wrong hashCode → wrong bucket → get() returns null!
class Employee {
  private int id;
  public boolean equals(Object o) {
    if(!(o instanceof Employee e)) return false;
    return id==e.id;
  }
  public int hashCode() {
    return Integer.hashCode(id); // SAME field!
  }
}
Set<Employee> s=new HashSet<>();
s.add(new Employee(101));
s.contains(new Employee(101)); // true
Mistakes: Override equals only · Different fields in hashCode · Mutate key after putting in HashMap · HashSet uses HashMap internally (keys = elements)
Q: Why hashCode with equals?
HashMap finds bucket via hashCode, exact match via equals. Breaking contract = silent data loss.

4. Immutability

Object cannot change after creation. Any "change" creates a new object. String, Integer, LocalDate are immutable.
String name = "Ashish" name ──► [A|s|h|i|s|h] (fixed) name.concat(" Shah") → NEW object [Ashish Shah] → name still "Ashish"!

Benefits: Thread-safe · Safe HashMap keys (hash never changes) · Predictable · Secure for passwords · Can share without copying

How to Make Immutable Class

  1. final class (no subclass)
  2. private final fields
  3. No setters
  4. Defensive copy for mutable fields (List, Date)
public final class Person {
  private final String name;
  private final List<String> tags;
  public Person(String n, List<String> t) {
    name=n; tags=List.copyOf(t);
  }
  public String getName(){return name;}
}
// Java 17 Record — immutable by default
public record User(Long id, String email){}
Interview: Why String is good HashMap key? hashCode never changes because object never mutates.

  int add(int a,int b){return a+b;}

}

Q: Overload vs Override?
Overload = same name, different params, same class, compile-time. Override = child replaces parent method, runtime decision.

7. HashMap Internals — Complete Breakdown

Simple: Array of buckets. Key → hashCode() → bucket index → store/lookup. Like numbered mailboxes in a building. Average O(1) lookup.
Node<K,V>[] table (default size 16, power of 2) [0]→null [1]→(Banana→v) [2]→null [3]→(Apple→v)→(Apricot→v) ← collision: linked list ... [15] List >8 in bucket + table≥64 → Red-Black Tree Load factor 0.75 → size > cap×0.75 → DOUBLE + rehash

put(key, value) Steps

  1. hash = spread(key.hashCode())
  2. index = (table.length-1) & hash
  3. Bucket empty → insert Node
  4. Collision → linked list/tree, check equals()
  5. Over threshold → resize ×2, rehash all

get(key) Steps

  1. Compute hash → bucket index
  2. Traverse bucket, compare equals()
  3. Return value or null

11. Deadlock  ·  12. Java Memory Model (JMM)

11. Deadlock

Threads wait for each other forever. Each holds a lock the other needs. Nobody proceeds.
Thread 1 Thread 2 lock A ✓ lock B ✓ wants B → WAIT wants A → WAIT ─────── DEADLOCK ─────── 4 Coffman Conditions (ALL required): 1.Mutual exclusion 2.Hold-and-wait 3.No preemption 4.Circular wait
Object lockA=new Object(), lockB=new Object();
// Thread 1
synchronized(lockA){ synchronized(lockB){} }
// Thread 2 — OPPOSITE ORDER = DEADLOCK!
synchronized(lockB){ synchronized(lockA){} }

Prevention

  1. Lock ordering — always A then B everywhere
  2. tryLock(timeout) — don't wait forever
  3. Minimize lock scope
  4. Detect: jstack → "Found Java-level deadlock"
Q: What is deadlock?
Two threads circular-wait for locks. Fix: consistent lock order, tryLock with timeout.

12. Java Memory Model (JMM)

Rules for how threads see memory — visibility, ordering, atomicity across CPU cores.

3 Problems JMM Solves

  • Visibility — T1 sets x=1, T2 still sees 0 (CPU cache)
  • Ordering — CPU reorders instructions; T2 sees partial object
  • Atomicity — count++ = read+add+write; two threads lose increment
ToolVisibilityAtomicity
volatileYesNo (for i++)
synchronizedYesYes (in block)
AtomicIntegerYesYes (CAS)
final fieldsYes (post-construct)N/A

Happens-Before Rules

  • Unlock → subsequent Lock (same monitor)
  • volatile write → subsequent volatile read
  • thread.start() → actions in new thread
  • Thread actions → thread.join() returns

15. LRU Cache Design

LRU = Least Recently Used. Fixed capacity cache. When full, evict the item not accessed longest. Like a small desk — remove the paper you haven't looked at in the longest time.

Operations (Capacity = 3)

put(A) → [A] put(B) → [A,B] put(C) → [A,B,C] ← full get(A) → [B,C,A] ← A = most recent put(D) → [C,A,D] ← B evicted (least recent) MRU (head) ──────────────► LRU (tail/evict)

Approach 1: LinkedHashMap

class LRUCache<K,V> extends LinkedHashMap<K,V> {
  private final int cap;
  LRUCache(int cap) {
    super(cap, 0.75f, true); // access-order
    this.cap = cap;
  }
  protected boolean removeEldestEntry(
      Map.Entry<K,V> e) {
    return size() > cap;
  }
}
// get(1) then put(4,D) evicts key 2

Approach 2: HashMap + Doubly Linked List (Interview)

HashMap: key → Node (O(1) lookup) DLL: HEAD(MRU) ↔ nodes ↔ TAIL(LRU) get(key): map lookup → move to HEAD O(1) put(key): exists → update, move HEAD O(1) new+full → remove TAIL, add HEAD O(1) new+space → add at HEAD O(1) Total: get O(1), put O(1), Space O(cap)
void get(int key) {
  if(!map.contains(key)) return -1;
  Node n=map.get(key);
  moveToHead(n);
  return n.val;
}
void put(int key,int val) {
  if(map.contains(key)) updateMoveToHead(key,val);
  else {
    if(map.size()==cap) removeTail();
    addToHead(key,val);
  }
}
Q: Design LRU Cache O(1)?
HashMap for O(1) lookup + DLL for O(1) move/evict. HEAD=MRU, TAIL=LRU.

Top 10 Interview Q&A

Q1. HashMap internals? Bucket array. hashCode()→index. Collision→list→tree if >8. Load 0.75→resize×2.

Q2. == vs equals? == = reference. equals = content. Use equals for objects.

Q3. String vs StringBuilder? String immutable (new object each concat). StringBuilder mutable, fast.

Q4. Abstract vs Interface? Abstract: 1 inheritance, shared code. Interface: multiple, capability.

Q5. Overload vs Override? Overload: same class, diff params, compile-time. Override: child replaces, runtime.

Q6. Deadlock? Circular lock wait. Fix: consistent order, tryLock timeout.

Q7. volatile vs synchronized? volatile=visibility. synchronized=visibility+mutual exclusion.

Q8. ArrayList vs LinkedList? ArrayList O(1) get. LinkedList O(n) get. Use ArrayList.

Q9. How GC works? No references→eligible. Young=minor GC. Old=major GC. G1=Java 9+ default.

Q10. Design LRU Cache? HashMap O(1) lookup + DLL O(1) move/evict. Remove tail when full.
